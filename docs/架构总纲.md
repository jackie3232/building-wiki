> 用途：本项目架构的「总纲」——不可漂移的结构性约定。
> 凡涉及架构的修改，都要回来核对这些条款是否仍满足；不满足即须显式说明并更新本文件。
> 写法：逐条追加，每条 = 【条款 + 判据 + 依据】。依据一律指向实盘文件/代码。
> **性质：本总纲是「目标态」架构约定（应做成什么样子），不是对当前代码现状的描述。** 条款 / 判据只写目标；现状与目标的落差放进各条「待核」小节，不混入条款与依据正文。

## 1 · 驱动范围（Agent 驱动）

**条款**
应用分两层——**驱动层 = Agent**（含它调用的一切：函数内脚本、云托管的自动化引擎）；
**交互层 = 前端**（只做输入与展示）。

**数据流**
前端输入 → 前端以 **ACP** 调 Agent → Agent 全程执行（理解 / 装配 / 上传 / 调 MCP）→
结果经事件流回传 → 前端渲染。

**判据**
1. 前端零业务逻辑（只收发 + 渲染）。
2. 前端调的是 **Agent**（`/acp` 端点），不是自动化端。
3. 自动化端虽独立部署，但逻辑上属驱动层——只被 Agent 调用。

**附**
体素数据走云存储直连（预签名 URL）：**Agent 只回传引用，不搬数据**。

**依据**（实盘，2026-09-27 核实）
- `web/config.js` → `ACP_URL = .../v1/aibot/bots/agt-building-8gp5in9y2e59d69c/acp`
- `web/app.js` `runAgent()` → `fetch(ACP_URL, { jsonrpc:"2.0", method:"session/prompt", ... })`
- `web/app.js` → `fetch(state.boxes)` 直连拉取体素数据
- `server/cloudbaserc.json` → `cloudrun.name = "building-wiki"`（自动化端独立部署）
- `functions/agt-building-8gp5in9y2e59d69c/agent.yaml` + `scf_bootstrap`（Agent 为云函数）

## 2 · 技能定位（skill = 场景作业标准）

**条款**
skill = **一个场景的固化工作流**（作业标准），与 Agent **一一对应**
（设计约定，非平台强制——平台本身允许一个 Agent 挂多个 skill）。

**技能组成**
手册（流程 + 红线 + 契约）+ 脚本（确定性工具）+ `packs`（数据）。

**执行归属（本条要点）**
**技能本身不是执行者**；执行的发起者始终是 **Agent**。
技能只**提供给** Agent：规定它该怎么做（手册）、给它工具（脚本）、给它依据（packs）。
即：**技能规定 Agent，Agent 执行；技能自己不动作。**

**判据**
1. Agent 行为必须由 skill 手册规定，不得自创流程。
2. 技能不承载风格事实，风格全部下沉 `packs`。
3. **当前形态：单专家 + 单 Agent + 单 skill + 多风格知识包**（1 : 1 : 1）。
   「多」只发生在**数据层**（`packs/<style>/`），不发生在线路层（Agent / skill）。
   多专家**不在当前范围内**，不据此设计。

**代价（明记）**
一一对应 ⇒ 多专家要多套部署单元；换来的是「一个专家 = 一个可独立打包的单元」。

**依据**（实盘，2026-09-27 核实）
- `functions/agt-building-8gp5in9y2e59d69c/skills/` 下仅 `traditional-building` 一个（1:1 现状）
- `.../traditional-building/packs/` 下 `siheyuan` + `jiangnan` 两个（技能不承载风格事实）
- `SKILL.md` 的 frontmatter（`name`/`description`）+ 正文流程 = 作业标准
- `assemble.mjs` / `upload_instance.mjs` = 脚本，由 Agent 用 Bash 调用
- OAK `skills.enabled` 支持数组（平台允许 1:N，我们选 1:1）

## 3 · 专家定位（专家 = Agent 的人设）

**条款**
「专家」在本架构中**不是独立层、没有独立工件**；它 = **Agent 的人设**（`agent.yaml` 的 `system` 字段）。
因此：**1 个专家 = 1 个 Agent = 1 个人设 = 1 个 skill**（与总纲 1、2 的 1:1 一致）。

**边界**
技能 = 怎么做（`SKILL.md`）；人设 = 是谁 / 懂什么 / 守什么（`system`）。互补不重叠，同挂一个 Agent 名下。

**判据**
1. 不存在 expert 独立文件 / 目录。
2. 专家身份只写在 `system` 一处。
3. 人设只管「是谁 / 懂什么 / 守什么」，流程一律归 `SKILL.md`。

**依据**（实盘 + 官方，2026-09-27 核实）
- 官方 `/ai/agent/knowledgebase` 字段说明：`system` = 「人设 / 系统提示词」
- OAK `createAgent` 全 20 字段无 expert / persona
- 实盘 `functions/agt-building-8gp5in9y2e59d69c/` 下无 expert 工件

## 4 · 智能 / 自动化分界

**条款**
分界 = **实例图谱**（自包含 JSON），**不是进程 / 部署边界**。
智能侧 = ① 理解（LLM）+ 装配（确定性脚本）；自动化侧 = ④ 几何计算 + ⑤ 造型。

**衔接三要素**
1. 通道：`cos:instances/<uuid>.json`（云存储）
2. 契约：MCP 工具 `generate_building(instance_ref)`
3. 内容：图谱自包含（`data` + 知识中心全量快照：dict / type graph / rules）—— 装配出口将**本风格知识中心三件套整份以快照嵌入**实例图谱；自动端只读此自包含快照，绝不回读 pack（与判据 1 / 2 一致）。

**判据**
1. 自动化端不引用知识包（容器不 COPY packs）。
2. 自动化端只吃图谱快照。
3. 自动化端输出**体素 BOX 数据**，不输出「模型」——模型由前端渲染。

**附**
智能侧装配出口有一道**实闸**（即总纲 6 的实例图谱校验，唯一质量闸门）；自动化侧 ④⑤ 之前是**消费已过关快照的概念点**，只吃已验证的实例图谱、**不重复校验**——两处共用同一事实源（已验证的实例图谱）。**硬闸 ≠ 分界**：硬闸是质量概念（校验一次），分界是数据概念（实例图谱 JSON）。

只留 `ping` + `generate_building`（见总纲 5）。

**依据**（实盘，2026-09-27 核实）

- `server/Dockerfile` 管线注释：「Agent（LLM 出骨架 → skill 装配实例图谱）→ MCP generate_building（内部 ④ compute_geometry → ⑤ geometry_to_boxes）→ 客户端渲染（前端独立部署，不在本容器内）」

## 5 · MCP 职责（单入口）

**条款**
MCP（自动化端）**只做一件事**：吃实例图谱 → 出体素数据（④ 几何计算 + ⑤ 造型）。
对外**单入口** `generate_building(instance_ref)`（by-reference，④⑤ 一体化），
外加一个 `ping` 做冒烟。**不**把 ④ / ⑤ 各自单独暴露成工具。

**判据**
1. MCP 不碰知识包、不做智能判断（只做确定性计算）。
2. Agent 只需认识**一个**几何工具——不必知道 ④⑤ 的分步。
3. 「按引用读回实例图谱」是该入口的**内部步骤**，不是一次工具调用。
4. 出参与入参对称走引用：入参 `cos:<key>`，出参云存储预签名 URL（绕开 harness 对大输出的截断）。

## 6 · 实例图谱校验（核心数据交付关卡）

**条款**
实例图谱校验 = 智能化侧（①理解 + 装配）与自动化侧（④几何 + ⑤造型）之间**核心数据交付的关卡**：图谱越过此关，才被允许作为自动化侧的输入。校验**只在智能侧装配出口一处**发生（见判据 1），自动侧不重复。

**判据**
1. 校验发生在智能侧装配出口（与总纲 4「智能侧硬闸」同义）。
2. 它是跨越智能 / 自动分界的唯一质量闸门；自动化侧只吃已过关的图谱，不再重复校验（与总纲 4 / 5 一致）。
3. 校验范围严格限定图谱自身合法性（对本体三层一致性 + 实例完整性），**不查几何 / 造型**（那属自动化侧，且自动侧不重复校验）。

**校验域（实例图谱 vs 本体 一致性）**
实例图谱 = 本体(dict + type graph + rules) + 参数（总纲 8）。校验 = 实例图谱对本体三层的一致性 + 实例自身完整性，逐层收窄：
- **域① 命名合法性（对 dict）**：实例引用的角色 / 构件 / 方位 / 材质，必须命中 dict 单一命名权威；未定义词 = 图谱缺陷。
- **域② 结构 / 组合合法性（对 type graph）**：(a) `type.ref` 守卫——type 内所有 `ref` 必须命中 dict key，否则报图谱缺陷（总纲 8 判据 2(a)）；(b) 拓扑组合须符合 type graph 定义的院落 / 中轴结构（typed-graph 兼容：实例每个节点在 type graph 有对应类型）。
- **域③ 约束符合性（对 rules）**：实例须满足 rules 的 occupancy / position / paramRanges 约束（如垂花门仅一↔二进、后门仅末进）。
- **域④ 实例自身完整性（ABox）**：实例图谱自包含（data + appliedRules + appliedDict 齐备）、必填字段存在、值域合法（数值 / 枚举在范围内）。

**依据**（实盘核实）
- `functions/agt-building-8gp5in9y2e59d69c/skills/traditional-building/assemble.mjs:550-708` `validateInstanceGraph` —— 实例图谱硬闸唯一实现；`:771` 装配出口调用（注释「服务端不再重复校验」）。
- 总纲 4「附」：智能侧装配出口一道实闸（= 本条第 6 点校验，唯一质量闸门），自动化侧 ④⑤ 之前只消费已过关快照、不重复校验，两处共用同一事实源；硬闸 ≠ 分界。

## 7 · 解耦性（不变 / 可变 二分 + 知识中心注入）

**条款**
本 Agent 架构按「不变 / 可变」二分：
- **可变** = 知识中心（packs）：不同中式传统建筑类型的知识，作为数据灌入。
- **不变** = 框架 / 引擎：代码定完即固定，不随建筑类型变。
- **边界**：Agent 定位「中国传统建筑之家」→ 知识中心收录范围锁定中式传统建筑。
解耦靠一条契约：知识中心只通过约定的格式（图谱 schema / rules 字段）注入，引擎只认契约、不认内容——换一种建筑 = 换一份知识包，引擎零改动。

**判据**
1. 引擎零风格硬编：不出现任何具体建筑类型 / 角色名 / 进数 / 拓扑字面量。
2. 新增 / 切换建筑类型只改知识中心，不改框架代码（零引擎改动）。
3. 知识中心内部组织形态不在本条讨论范围（留待后续）。

**案例（机制的可视化验证）**
- 注入「北京四合院」知识 → 复现北京四合院；
- 注入「江南风格」建筑知识 → 创建江南风格建筑；
- 注入「阿房宫」特定建筑知识 → 复现阿房宫。
同一份框架，靠数据灌入差异支撑不同类型建模。

**依据**（实盘核实）
- `functions/agt-building-8gp5in9y2e59d69c/skills/traditional-building/assemble.mjs:58-62` `loadKnowledge(style)` 取 `packs/<style>/{*.rules,*.type.json,dict.json}`；`:724-725` `style` 来自 `plan.style`。
- 总纲 2 判据 2「技能不承载风格事实，风格全部下沉 packs」；判据 3「多只发生在数据层」。
- 总纲 4 判据 1「自动化端不引用知识包」。
- `packs/` 下 siheyuan（已落地）、jiangnan / epanggong（规划，对应上述案例）。

## 8 · 知识中心（可变部分的总和 + 内部组织）

**条款**
知识中心 = 总纲 7 所说「可变」部分的总和，由若干 **知识包（pack）** 承载，每个 pack 对应一种中式传统建筑风格（`packs/<style>/`）。
两条生命线：
- **进（维护）**：**人主导，AI 辅助整理材料**——由人把一本书 / 一类风格吃透、做知识工程（结构化抽取入库），AI 不回写事实源。
- **用（消费）**：Agent 确定性消费 pack，引擎零改动。
进侧愿景：人主导 AI 理解 **一本书 = 一类中国传统建筑风格** → 知识工程 → 塞入一个 pack → 产出该风格的三维模型。

**判据**
1. 进由人主导；LLM 只辅助整理，绝不回写事实源（事实源 = pack 文件）。
2. 每个 pack 内三件套，定位与**顺序**严格如下（**顺序关系，非依赖堆叠**）：
   - **命名字典 `dict.json`** = 词汇层 / 唯一命名权威（外部对标 bSDD / Data Dictionary，ISO 12006-3）：定义「有哪些词、每个词是什么」（空间角色 / 构件 / 方位 / 材质……）。type / rules 只能 `ref` 引用，不得另起名字。
   - **类型图谱 `*.type.json`（class graph）** = 结构 / 组合层（外部对标 IFC 实体-关系 schema / 图论 type graph）：定义这些角色**如何组织、组合、拓扑、关联**。按 (a) 决策——**只组织、不重声明角色名**，角色名全走 `ref` 锚定 dict key；结构属性（level / material / modular / structs）留在 type 按 ref 挂。
   - **规则库 `*.rules`** = 约束层（外部对标 IDS / 本体公理）：定义**必须遵守什么约束**（occupancy / position / paramRanges），即总纲 6 校验器的知识源。
   - **本体（Ontology）= 命名字典 + 类型图谱 + 规则库 三者之和**（概念模型整体：词 + 结构关系 + 约束公理，对标 OWL 本体）。
   - **实例图谱 = 本体 + 实例参数**：本体被具体建筑实例化（几进、具体尺寸、哪些角色落地），即总纲 4 的实例图谱（ABox）。
   - **公式（本条第 2 款收口）**：`instance graph = ontology( dict + type graph / class graph + rules ) + parameters`
     - 外部取经背书：图论 typed graph（instance graph 每节点须在 type graph 有对应类型）、描述逻辑 TBox/TBox+ABox——与上式严格同构（2026-09-28 核实）。
   - **序列化 = JSON，非 OWL**：三件套以 `dict.json` / `*.type.json` / `*.rules` 三个 **JSON 文件**落盘与读写；OWL 仅作**概念对标**（本体建模思想同构于 OWL TBox/ABox），不作存储介质。引擎只做查表 + 校验（按 key 查 dict、type.ref 命中 dict、套 rules），无需 DL 推理，故不引入 OWL/RDF 解析与推理机依赖（与总纲 7 判据 1 零风格硬编、双运行时零重依赖一致）。
3. 引擎零风格硬编（与总纲 7 判据 1 一致）；切换风格只换 pack。
4. 治理边界：pack 准入审核、版本化、与实例图谱的可追溯等治理问题不在当前架构范围，留待后续；当前默认**单实例对应单 pack**（与总纲 7 判据 3 一致）。

**案例（顺序的可视化）**
建「北京四合院」pack：先有 `dict.json` 定义 zhengfang / xiangfang / … 等词 → `siheyuan.type.json` 用 ref 把这些词组织成院落 / 中轴拓扑 → `siheyuan.rules` 约束垂花门仅一↔二进、后门仅末进等 → 三者合成四合院实例图谱。江南 / 阿房宫同构，仅换 pack。

**依据**（实盘 + 外部取经，2026-09-28 核实）
- 外部标尺（buildingSMART 生态 + 知识工程三层）：bSDD = 定义词 / Ontology = 定义关系与结构 / IDS = 定义约束并校验；与「命名字典 → 类型图谱 → 规则库」逐层同构。
- (a) 决策（宪法层面）：`type` **不重声明角色名**，角色名全走 `ref` 锚定 dict key；`validateInstanceGraph` 须含「`type.ref` 必须命中 dict key，否则报图谱缺陷」守卫（与总纲 6 校验域②一致）。实盘落点 `assemble.mjs:550-708` `validateInstanceGraph`。
- `assemble.mjs:58-62` `loadKnowledge(style)` 取 `packs/<style>/{*.rules,*.type.json,dict.json}` —— 三件套即 pack 的承载形态。
- 总纲 7「可变 = 知识中心（packs）」「判据 3 内部组织留待后续」→ 本条即该后续。
